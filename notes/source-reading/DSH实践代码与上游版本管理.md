## 基本安排

- `/Users/wuhaixu/Desktop/deepseek-harness`：官方源码检出，用于运行、阅读和查证 DSH 实现；主目录保持干净，在实验之间更新。
- `/Users/wuhaixu/Desktop/我的空间/dsh-study`：个人学习仓库，保存课程笔记、实验、插件、配置、测试和报告。

自己的实验和扩展主要在 `dsh-study` 中开发。确实需要修改 DSH 本体时，在 DSH 仓库建立个人分支，优先使用独立 worktree。

## 修改放在哪里

| 修改内容 | 存放位置 | 版本控制归属 |
| --- | --- | --- |
| 课程笔记、源码阅读记录 | `dsh-study/notes/` | 学习仓库 |
| 极简 Agent 循环、评测代码、实验网页和报告 | `dsh-study/labs/<三位编号-主题>/` | 学习仓库 |
| 自定义工具、Skills、事件插件和配置覆盖 | 对应实验目录中的独立插件包和配置 | 学习仓库 |
| DSH 已有实现的必要修改 | DSH 个人分支，优先在独立 worktree 中开发 | DSH 仓库；远程保存到个人 fork |

持续发展的 Coding Agent 保留一份插件源码。后续实验引用它，保存各自的配置、被测版本与结果，避免每个课程模块复制一套插件。

实验网页和待修复项目作为明确指定的 Agent 工作区；启动时确认工作区选择，避免无意中把 DSH 框架源码作为修复目标。

## 外部插件如何接入

DSH 支持通过 `--patch` 覆盖层加载本地插件，也支持将外部插件组合包安装到指定 profile。自己的浏览器诊断工具、验收策略等可以在学习仓库中开发，再加载到 DSH 中运行。

独立插件包应声明自己的依赖和构建方式，并保存对应的依赖锁文件。插件包的依赖版本需要与所用 DSH 版本兼容，不能依赖源码目录的偶然相对位置来解析依赖。

可复用配置、安装和启动步骤保存在学习仓库中。机器本地的 profile 和运行目录由这些配置与步骤重建。

实现时查阅当前检出的 [插件安装说明](/Users/wuhaixu/Desktop/deepseek-harness/docs/user/develop/basic/publish.zh.md) 和 [CLI 行为参考](/Users/wuhaixu/Desktop/deepseek-harness/apps/cli/reference/README.zh.md)，应用继续通过具名 `dsh` profile 启动。

## 每轮固定实验基线

一轮实验开始时，在该实验的 README 或报告中记录：

- DSH 的完整 Git commit。
- 被测实验代码和插件的 Git commit；如有未提交修改，应说明，不能仅用 HEAD 代表实际被测内容。
- 安装、构建和启动方式。
- 实际使用的配置、模型标识及相关运行条件。
- 对应的依赖锁文件。

可以在相应仓库执行 `git rev-parse HEAD` 获取完整提交号。实验报告中的提交号应来自当次实际环境。

实验进行期间保持基线稳定。分开仓库减少代码混杂和 Git 冲突；上游 API 的变化仍可能要求适配个人插件。兼容性通过固定版本和复测来检查。

## 在实验之间更新上游

1. 保存并提交自己的实验代码、配置和记录。
2. 确认 DSH 主目录工作区干净，且当前分支及其跟踪关系符合预期；没有分叉时使用 `git pull --ff-only` 更新官方代码。若无法快进，先检查分叉原因。
3. 按新版本要求安装依赖、构建，准备与新源码一致的运行产物。
4. 用固定任务检查启动、插件加载、工具调用，以及原来的端到端任务。
5. 验证通过后，在后续实验记录中采用新的 DSH 基线；失败则记录问题，决定适配或继续使用此前基线。

实验过程不自动追随每次远程更新。需要保留旧版本运行时，使用旧提交的独立检出或 worktree，并准备该版本自己的依赖与构建产物。

## 必须修改 DSH 本体时

DSH 主目录继续跟随官方 `master`。为个人实验创建诸如 `study/<实验主题>` 的分支，并放到独立 worktree 中修改。

worktree 是同一个 Git 仓库的另一份工作目录，可以同时保留官方版本和实验版本。个人修改提交到实验分支；检查、文档和测试要求遵循该 DSH 检出的 `AGENTS.md`。

需要远程保存这些改动时，创建个人 GitHub fork，并采用以下远程命名约定：

- `upstream`：官方 DSH 仓库。
- `origin`：个人 fork。

这是创建 fork 后采用的约定，不表示当前检出的远程已经被更改。个人改动推送到个人 fork 的实验分支；在实验阶段结束时，将上游更新合入该分支并验证。版本记录中同时保留官方基线和包含个人修改的被测提交。

主要开发外部插件的阶段，可以先维持现有两个仓库，不必预先增加 fork 和 worktree。

## 隔离运行数据

实验使用独立的 `DSH_HOME`。升级试验优先使用新的运行数据目录，让不同版本的实验可以各自重建和验证。

Git 退回旧提交不代表新版会话数据可以降级读取。需要返回旧代码基线时，使用该基线对应的实验数据或新建运行目录，不假定旧版本能够打开新版产生或迁移的数据。

运行目录通常不进入 Git；用于重建环境的配置模板与步骤应进入学习仓库。

## 提交与忽略范围

开始代码实验时维护 `.gitignore`，明确以下范围：

| 内容 | 处理方式 |
| --- | --- |
| 源码、测试、配置模板、依赖锁文件、安装启动说明 | 提交 Git |
| 实验报告、经过检查且必要的运行证据 | 提交 Git |
| `node_modules`、可重建的构建产物、临时运行目录 | 忽略 |
| `.env`、凭据和带有密钥的本地配置 | 忽略；仅提交无秘密的示例配置 |
| 大体积原始会话、缓存和临时输出 | 默认忽略；在报告中说明证据位置和重现方式 |

按实验或功能形成小提交，确保能辨认每次机制改动及其验证结果。提交前检查 diff，仅暂存本次明确涉及的文件。依照学习仓库约定，未经明确要求不代用户提交、推送、发布或部署。

## 日常工作方式

在 `dsh-study` 修改自己的插件和实验，使用固定版本的 DSH 运行，带着具体问题回到 DSH 源码中查证。每轮实验结束后，再决定是否升级上游或进入 DSH 本体开发。
