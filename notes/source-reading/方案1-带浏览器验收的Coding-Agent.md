# 方案1：带浏览器验收的 Coding Agent

记录日期：2026-09-11

状态：已确认为方案1，尚未开始实现和端到端验证。

## 目标与学习方法

基于 DeepSeek Harness，做一个会自己打开浏览器、复现问题、修改代码、再次操作并验收的 Coding Agent，随后逐步深入视觉 Computer Use。最终达到能够按自己的想法自定义 Agent 能力和工作方式的程度。

采用用户认可的 Karpathy 式学习方法：

1. 持续完成具体项目，遇到问题时按需学习，并沿着项目深入。
2. 每轮用自己的话总结和讲解所学内容。
3. 与过去的自己比较，观察定位问题、选择扩展点和独立验证的能力是否提高。

以同一个 Agent 的连续迭代贯穿学习。已有的 [DSH 源码学习计划](DSH源码学习计划.md) 和 [学习路线](../../ROADMAP.md) 作为按需查阅的背景资料。

## 贯穿案例

用户给 Agent 一句话：

> 这个看板拖动卡片后，刷新页面就恢复原样了。你自己复现、修好，再验证。

Agent 应实际完成：

```text
打开网页
→ 操作并复现问题
→ 查找相关代码
→ 修改代码
→ 刷新并重复原来的操作
→ 按事先确定的条件验收
→ 展示修改与操作证据
```

网页是用于检验 Agent 能力的任务环境。学习中持续改进的是 Agent 的工具、配置、观察方式、验收流程和停止条件。

## 分阶段路线

| 阶段 | 要做出的东西 | 完成标准 | 按需深入的内容 |
| --- | --- | --- | --- |
| 1. 第一次自主修复 | 给 Agent 一个有明确 Bug 的本地网页，让它实际复现、修复和重试 | 能展示修改前的失败、代码改动和修改后的成功操作；浏览器验收确实执行 | 文件与命令工具、浏览器接入、工具结果如何影响下一步 |
| 2. 完成开发需求 | 例如给看板增加搜索与筛选，并逐项操作验证 | 需求逐条对应到实际页面行为，开发服务器可正常启动和使用 | 任务拆解、开发服务器管理、验收条件、代码与页面状态 |
| 3. 开发自己的 Agent 能力 | 写一个浏览器诊断工具，汇总当前页面、控制台错误和截图 | 工具能被 Agent 调用，结果能帮助定位问题；所选视觉模型确实能接收截图 | 插件注册、工具输入输出、附件、模型上下文和会话记录 |
| 4. 改造工作方式 | 验收失败继续修，重复失败停止并报告卡点，允许用户随时打断 | 能演示成功停止、失败后继续、预算耗尽停止和取消清理 | 事件、停止条件、可配置预算、取消与资源清理 |
| 5. 视觉 Computer Use | 根据截图定位目标，用鼠标键盘操作，再观察结果；之后扩展到桌面应用 | 在选定任务中完成截图、判断、动作、再观察的全过程，并能处理动作失败 | 视觉模型、坐标与缩放、动作后的等待、错误恢复、桌面执行器 |

推荐先完成前三阶段，再挑战纯视觉操作。优先复用已有插件，并通过文档化扩展点增加行为；需要修改某个子系统时，再阅读该部分源码和适用的仓库规范。

## 两种操作路径

### 浏览器结构操作

读取按钮、输入框等网页结构，再点击、输入和验证。初期考虑通过 Playwright MCP 接入，用可访问性快照为 Agent 提供页面信息。它属于浏览器自动化，不等同于纯截图驱动的视觉操作。

### 视觉 Computer Use

让模型看截图、判断操作位置、执行鼠标键盘动作，然后重新截图观察。需要真实支持图片输入的模型，以及截图、鼠标和键盘执行器。原生桌面应用控制作为后续扩展，届时再选择和验证执行器。

## 每轮学习与记录

每轮从一个真实失败或想改变的行为开始，例如：

> 它没有打开页面，为什么就说修好了？

围绕这个问题定位扩展点、实现修改，再用运行结果判断是否解决。总结时用自己的话回答：

1. 这次想改变什么行为？
2. Agent 原来依据什么信息作决定？
3. 改了哪个配置、工具或事件扩展点？
4. 什么证据说明改造生效？还有什么未验证？
5. 换一个类似 Bug，这次改造是否仍然有效？

可复现实验按仓库约定放入 `labs/<三位编号-主题>/`，记录目的、环境、步骤、结果和结论。隔几轮尝试一个相近需求，比较自己找到入口、定位错误和独立验证时需要多少帮助。
