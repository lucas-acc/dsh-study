## 第一次：让 DSH 修一个小程序

### 本次看什么课

暂时不用看课。先获得一份自己亲眼看到的 Agent 执行过程。

### 具体做什么

**1. 准备一个独立的小实验目录。**

建议使用 `labs/001-first-repair/`，实际创建时若编号已占用，顺延。目录中先放 `add.cjs` 和记录用的 `README.md`。以下是待创建的文件内容，本指南不会自动创建或运行实验。

`add.cjs`：

```js
const assert = require('node:assert/strict');

function add(a, b) {
  return a - b;
}

assert.equal(add(2, 3), 5);
assert.equal(add(-2, 3), 1);
assert.equal(add(0, 0), 0);
console.log('全部通过');
```

这里使用会抛出异常的断言，让失败体现在命令退出状态中。验收不能仅依赖 Agent 的文字描述。

**2. 自己先运行一次，保留失败输出。**

在实验目录执行：

```sh
node add.cjs
```

预期：第一条断言失败。若找不到 Node，先处理运行环境；还没有进入 Agent 学习环节。

**3. 在这个实验目录启动 DSH。**

如果本机已经安装了可用的 `dsh`，可以在实验目录执行：

```sh
dsh --profile web
```

当前本地 [CLI 参考](/Users/lucas/Desktop/my-projects/deepseek-harness/apps/cli/reference/README.zh.md) 说明，基于 base 的 profile 默认使用启动目录作为 workspace。启动后仍需确认当前会话的工作区确实是实验目录，以及所选模型可以响应并调用文件和命令工具。

如果还没有可用的 DSH，先完成安装、模型配置和一次正常回复。使用源码启动时，按该 CLI 参考中的“源码执行”准备构建产物，并确认实际工作区；不要直接把 DSH 源码目录当成待修复项目。把实际可用的启动方式记入实验 README。

实验环境、独立 `DSH_HOME` 和配置组织遵循 [DSH 实践代码与上游版本管理](DSH实践代码与上游版本管理.md)。该文中的旧机器路径需要换成本机路径：学习仓库为 `/Users/lucas/Desktop/my-projects/dsh-study`，源码仓库为 `/Users/lucas/Desktop/my-projects/deepseek-harness`。首次准备独立运行环境时需要重新确认模型配置可用。

**4. 给 DSH 这句话。**

> 请先运行当前目录的 add.cjs，复现失败，再阅读代码并修复 add 函数。不要修改断言或删除测试。修改后重新运行，给出失败原因、改动和实际验证结果。所有文件修改限定在当前实验目录。

**5. 检查实际动作。**

- 是否运行了程序，拿到了失败输出？
- 是否读取、修改了代码？
- 是否重新运行，并出现“全部通过”？
- 是否保留了原来的三条断言？

模型可能采用不同的工具顺序。记录实际顺序，不要把预想流程当成执行记录。若它跳过了复现或验证，记下这次失败，再明确要求补做。

### 留下什么

保存原始 Bug 文件、修复差异、前后命令输出和 DSH 工具调用记录。记录启动方式、实际模型标识和 DSH 版本；源码运行还应记录提交号与构建情况。

你可以从记录中指出：哪一次工具调用失败了，失败输出在哪里，后续发生了什么修改，哪次运行验证了结果。

## 第三次：自己写一次极简 Agent 循环

### 本次看什么课

### 具体做什么

在 `labs/002-minimal-loop/` 做独立教学实验，建议使用 JavaScript，复用已经可用的模型服务。先让它完成一个更小的任务：“读取一个文本文件，把其中的错字修正，再读回确认”。

先提供两个工具就够：`read_file`、`write_file`。工具实现把文件操作限制在实验目录内。记录工具定义、每次调用参数、对应结果和停止原因。

自己实现以下控制流程；具体消息格式以所用模型服务的协议为准：

```text
构造用户任务和工具定义
→ 调用模型
→ 如果返回工具调用：执行，并回填与该调用对应的结果
→ 带着更新后的消息再次调用模型
→ 如果返回最终回答：结束
→ 如果达到预设的模型调用上限：停止并报告
```

先把上限设为 10 次模型调用。增加一次失败练习：要求读取不存在的文件，让工具返回清晰的错误结果，观察模型接下来如何处理。不要把模型回复的工具名硬编码成固定动作顺序。

随后回到 DSH 源码，在 `/Users/lucas/Desktop/my-projects/deepseek-harness` 中找到“构造模型输入、执行工具、回填结果、停止”四个职责的实现，记录当时的文件路径和函数。只沿这条调用路径阅读。

### 什么时候可以继续

程序真的调用模型并完成了读写任务；工具失败可以反馈给模型；步数上限有明确的停止记录。你能说明哪些代码由自己实现，并画出它与 DSH 的职责对应关系。

## 第五次：完成一次网页 Bug 修复

### 本次看什么课

看 Coding Agent、GUI Agent 中与复现、观察和验证有关的内容，结合 [方案1](方案1-带浏览器验收的Coding-Agent.md) 的贯穿案例。

### 具体做什么

准备一个最小看板：两列、一张可以拖动的卡片。故意让移动只更新内存状态，刷新后恢复原位。先由自己手动确认这个 Bug 存在，并保留可恢复的原始版本。

在交给 Agent 前写好验收条件：

- 将卡片从“待办”拖到“完成”，当前页面位置正确。
- 刷新后，卡片仍在“完成”。
- 拖回“待办”并再次刷新，仍保留新位置。

给 DSH 的任务：

> 这个看板拖动卡片后，刷新页面就恢复原样了。请用浏览器复现，定位并修改代码，再按这三条条件逐项操作验证。提交报告时给出复现证据、修改差异和每项验收结果。

若 Agent 只跑代码测试就宣布成功，把它记为“未完成浏览器验收”。若反复失败，先挑第一个明确卡点解决，例如没有拿到页面状态、工具报错没有反馈或定位到错误文件。

### 什么时候可以继续

保留了修改前的失败操作、代码差异以及修改后三条验收条件的实际操作记录。你能沿着记录说明，页面观察怎样帮助它定位和确认修复。

## 评估什么时候学

**第五次有了完整网页任务，就开始补充课程中的评估方法。** 若相应课程材料尚未发布，先执行本节的最低限度检查。

保留三个明确任务：

1. 已有固定任务：拖动后刷新，位置应保留。
2. 一个相近任务：修改卡片标题后刷新，标题应保留。
3. 一个留到改造完成才使用的新任务，例如新增卡片后刷新仍存在，用来初步检查迁移。

分别准备可复现的 Bug 初始版本和验收条件。前两个可用于反复开发；第三个在第一次验收后就已不再是未见任务，需要另留新任务。

每次改 Agent 后，先复测固定任务，再做保留任务。记录任务是否完成、是否真的执行浏览器验收、用了多少时间和调用。这样才能分辨某次改动只是适配了一个案例，还是也帮助了相近任务。

## 看 CMU 的具体规则

- **什么时候开始：** 第一次最小修复完成后就看，第二次学习专门留给课程。
- **每次看多少：** 看完当前主题中能回答实验问题的部分，就回到代码。可以先给看课留 30～60 分钟；这是节奏建议，不是必须看完的时限。
- **看什么形式：** 优先已公开的课件和作业说明，有录像再配合；不要默认每一讲都有公开视频。
- **课程没有更新到这里怎么办：** 记录缺失的材料，先做当前已经有文档支持的实验，发布后再补课。
- **要不要做原版作业：** 本路线先用 DSH 和本地练习覆盖学习目标；若以后选择完整做原作业，需要另按它的环境、任务和验收要求完成。
- **何时深入参考论文：** 当你无法解释实验行为，或需要选择改造方法时，挑对应论文读；暂缓训练、SFT 和强化学习实现。
